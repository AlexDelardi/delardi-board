# Access

The tool where the holder of `can_manage_access` manages people, their rights and their passcodes, and reads the login log. It is not on the home page or in the Tools menu yet: it is opened by its address, `access/`, until the single sign-in knows who is looking.

Three screens:

| Screen | What |
|---|---|
| People | add a person, role, sales rep name, switch off or on, show or issue a passcode |
| Rights | the matrix: people across, the 24 rights down, a tap switches one at once; the change history under it. On a narrow screen: one person at a time, as a list |
| Logins | who signed in to what (needs `can_view_logins`) |

Rules worth knowing:

- A person is switched off, never deleted: their name stays on tickets, tasks and notes. For the same reason a name cannot be changed after it is created.
- Switching off, and a new passcode, end that person's sessions at once.
- Nobody removes their own access to the tool or switches themselves off. Access to the tool is never copied to a new person.
- Every change is written to `acc_log`, and so is every look at a passcode.

## Passcodes

Sign-in everywhere checks a SHA-256 of the passcode, as before. A passcode issued here is generated by `access-api` (a word and four digits) and returned once to the access manager. A copy is stored encrypted with AES-256-GCM so it can be looked up later; the key is derived from the function secret `ACCESS_PASSCODE_KEY` (32 characters or more), which is not in the database. Passcodes set before the tool have no copy and cannot be shown. If the secret is missing, passcodes cannot be issued or shown and the page says so; everything else works. If the secret is changed, earlier copies can no longer be read and those people need a new passcode.

The page never keeps a passcode in its state: it lives in the dialog or the panel that shows it and goes with it.

## Files

| File | What |
|---|---|
| `app.js` | the page: language, People, the person panel, Rights, Logins, header, gate |
| `template.html` | the stylesheet around the shared kit (`ui/kit.css`) |
| `build.py` | builds `../index.html`: `python3 build.py` |
| `api/index.ts` | `access-api`, the only route to the data; a session gives a name, the database decides |
| `qa/mock.js`, `qa/test.js` | a stand-in for the API and the page's checks: `node qa/test.js` (`ONLY=`, `SHOTS=`) |
| `qa/api.test.cjs` | `access-api` itself, compiled and run in Node against a stand-in database: `node qa/api.test.cjs` |

The rules live in the database: `db/migrations/20261125_acc_1_access.sql` and `20261125_acc_2_session.sql`, checked by `db/tests/acc_t1_access.sql` (`db/dev/run_sql_tests.sh acc_`).
